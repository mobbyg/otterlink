# Building Distributable OtterLink Desktop Clients

This document is a planning and build guide for packaging the Qt 6 desktop client so people can run it **without installing Qt 6 or a development environment**.

The current client source is in `client/qt6/`. The person building a release needs a suitable Qt 6 SDK and compiler installed. The person receiving the packaged application should not need the Qt SDK, Qt Creator, CMake, or a compiler.

> **Important:** Packaging must be verified on a clean machine or virtual machine that does not have Qt installed. A client that runs on the developer's computer may be relying on DLLs, shared libraries, or Qt plugins that are only present there.

## 1. General release checklist

Before packaging a release:

- [ ] Start from a known Git commit or release tag.
- [ ] Build the client in Release mode, not Debug mode.
- [ ] Use a supported Qt 6 version and a matching compiler/toolchain for the target platform.
- [ ] Confirm the build succeeds from a clean build directory.
- [ ] Collect the executable/application bundle and all required Qt runtime libraries.
- [ ] Include the Qt platform plugin and any other plugins the client actually uses.
- [ ] Include required non-Qt runtime libraries when redistribution is permitted.
- [ ] Keep configuration, logs, and user data outside the application install directory where practical.
- [ ] Test login, server connection, chat, images/backgrounds, audio, TLS, and other features used by the release.
- [ ] Test on a clean system without Qt installed.
- [ ] Review third-party license and Qt LGPL/commercial-license obligations before distributing binaries.
- [ ] Publish a version number, release notes, supported platforms, and checksums.

## 2. Windows (64-bit)

The intended Windows deliverable is a self-contained folder or ZIP containing `otterlink.exe`, its runtime DLLs, and the Qt plugin directories it needs. Users should be able to extract the ZIP and launch the executable without installing Qt.

### Build requirements

- Windows 64-bit build environment.
- Qt 6 SDK with the **same compiler kit** used to build the application (for example, a MinGW Qt kit paired with its matching MinGW toolchain).
- CMake and the matching C++ compiler.
- The Qt modules used by this client: Core, Multimedia, Network, and Widgets.

Do not mix Qt builds from different Qt versions or compiler kits. For example, a MinGW-built client needs compatible MinGW runtime files; it cannot be packaged as though it were an MSVC build.

### Build the Release executable

Run these commands from a Windows development terminal, adjusting the Qt kit path and generator for the installed toolchain:

```powershell
cmake -S client/qt6 -B client/qt6/build-release -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="C:/Qt/6.x.y/mingw_64"
cmake --build client/qt6/build-release --config Release
```

Use the actual Qt installation path and kit name. The path above is an example, not a guaranteed location. If using an IDE-provided developer prompt or a different CMake generator, follow that generator's configuration requirements.

### Assemble the runtime folder

Use `windeployqt.exe` from the **same Qt kit** used for the build. Run it against the Release executable, directing its output into a clean staging directory. A typical command is:

```powershell
windeployqt --release --compiler-runtime --multimedia --dir dist/otterlink client/qt6/build-release/otterlink.exe
```

Check the installed `windeployqt --help` because supported options can vary between Qt versions. If the tool is not on PATH, invoke it using its full path inside the selected Qt kit.

The final package should be audited for the runtime components actually used by this client. In particular, verify the presence of:

- `otterlink.exe`
- Qt 6 runtime DLLs required by Core, Multimedia, Network, and Widgets
- MinGW runtime DLLs, if building with MinGW
- `platforms/qwindows.dll`
- `imageformats/qwebp.dll` if WebP images/backgrounds are supported by the build
- `tls/qschannelbackend.dll` if the client uses Qt's Schannel TLS backend
- The Qt Multimedia Windows plugin (commonly under `multimedia/`) if audio features require it
- Any additional Qt plugins or third-party libraries reported as dependencies by the build and deployment tools

Do not assume `windeployqt` has collected every dynamically loaded plugin. Qt plugins may be loaded at runtime, so exercise the relevant features on the clean test machine. Keep the directory structure generated by the deployment tool; Qt expects plugins in their proper subdirectories.

Package the complete staging directory as a ZIP, for example `OtterLink-Windows-x64-<version>.zip`. Do not ship debug symbols or development-only files unless intentionally providing a debug build.

## 3. macOS

For macOS, prefer distributing a correctly assembled `.app` bundle, optionally inside a DMG. The app bundle must contain the required Qt frameworks, plugins, and other runtime dependencies; the recipient should not need a separate Qt installation.

General process:

1. Build the Release target using a Qt 6 kit and Xcode/Apple Clang toolchain appropriate for the target architecture.
2. Ensure CMake produces the `.app` bundle.
3. Run `macdeployqt` from the same Qt installation on the app bundle. Check the tool's help for the installed Qt version.
4. Test on a separate Mac that has no Qt SDK installed.
5. For public distribution, plan for Developer ID code signing and Apple notarization. Re-test the signed/notarized artifact, not just the unsigned build.

Decide whether releases will target Apple Silicon, Intel Macs, or both. A universal binary is a separate build/configuration decision; do not assume one architecture's Qt libraries will work on the other.

## 4. Linux

A Linux build can be packaged so users do not need Qt installed, but Linux distribution compatibility needs particular care. Qt libraries can be bundled, while core system libraries (especially glibc) generally should not be copied blindly into an application bundle.

Possible release formats include:

- **AppImage:** convenient single-file distribution when the application and its permitted dependencies are bundled correctly.
- **Tarball directory:** an executable plus bundled Qt libraries and plugins, with a launcher that sets the appropriate library/plugin paths.
- **Distribution packages:** DEB or RPM packages that declare dependencies, if targeting particular distributions. These may rely on system packages and are not necessarily fully self-contained.

Recommended planning steps:

1. Build a Release version on the oldest supported Linux distribution (or a deliberately chosen compatible build environment).
2. Bundle the Qt libraries and plugins needed by the application using a maintained deployment workflow appropriate to the chosen format.
3. Check dependencies with tools such as `ldd` and inspect Qt plugin dependencies as well. Do not treat `ldd` alone as a complete audit of plugins loaded dynamically.
4. Test on clean installations of every supported distribution/version.
5. Verify multimedia, audio backend, TLS, image formats, fonts, and platform integration on those systems.
6. Document any remaining system-library or desktop-environment requirements.

Do not promise a single Linux binary will run on every distribution. Define a minimum supported Linux baseline and build/test against it.

## 5. Runtime configuration and user data

A distributable client must not depend on developer-specific absolute paths. Before a release:

- Confirm the server address can be configured appropriately for the release environment.
- Do not embed credentials, API secrets, or personal access tokens in the executable or package.
- Keep logs and writable settings in suitable per-user locations rather than assuming the install directory is writable.
- Provide a clear way to identify the client version when reporting a problem.
- Ensure errors caused by missing plugins or unavailable TLS backends are understandable.

If the client supports both development and production servers, document how the release chooses its server. Avoid accidentally shipping a build that points only to a local development server.

## 6. Licensing and third-party components

Qt and other dependencies have license and redistribution conditions. Before publishing a binary:

- Record the Qt version and modules included.
- Review the applicable Qt license terms for the chosen Qt distribution and modules, including LGPL/GPL obligations or commercial terms.
- Include required license notices and source-code/offer materials where the selected licenses require them.
- Check licenses for any additional bundled libraries, fonts, codecs, icons, and other assets.
- Do not assume that successful packaging automatically grants permission to redistribute every dependency.

This section is a checklist, not legal advice. Re-check the terms for the exact versions and modules being shipped.

## 7. Release testing

Test the **packaged artifact**, not just the executable in the build directory.

Minimum smoke-test checklist:

- [ ] Launches on a clean machine without Qt installed.
- [ ] Opens and closes cleanly.
- [ ] Connects to the intended OtterLink server over the expected transport.
- [ ] Login and logout work.
- [ ] Chat and direct messages work.
- [ ] TLS connections work where applicable.
- [ ] Images and WebP backgrounds load.
- [ ] Audio plays where supported.
- [ ] No required Qt plugin or runtime library is missing.
- [ ] Settings and logs are written to the expected user-writable location.
- [ ] No developer machine paths or test server addresses leak into the release.
- [ ] The archive extracts and launches using only the included instructions.

## 8. Suggested release directory layout

The exact layout depends on the platform and deployment tool. A Windows ZIP might look like:

```text
OtterLink-Windows-x64-<version>/
├── otterlink.exe
├── Qt6Core.dll
├── Qt6Gui.dll
├── Qt6Multimedia.dll
├── Qt6Network.dll
├── Qt6Widgets.dll
├── platforms/
│   └── qwindows.dll
├── imageformats/
│   └── qwebp.dll
├── tls/
│   └── qschannelbackend.dll
├── multimedia/
│   └── ... multimedia plugin(s), if required
└── README.txt
```

This is an illustrative checklist, not a complete fixed file list. Actual DLLs and plugin names depend on the Qt version, compiler kit, and features enabled. Prefer the deployment tool's output, then audit and test it rather than copying this example literally.

## 9. Future improvements

When release packaging becomes an active task, consider adding:

- A repeatable packaging script per platform.
- A versioned release process and Git tags.
- Automated clean-machine smoke tests.
- A release archive checksum and signed release notes.
- A CI build matrix for supported operating systems and architectures.
- A short end-user README with installation, first launch, server setup, and troubleshooting steps.

The goal is that developers need Qt to build OtterLink, but end users only need to download, extract/install, and run the packaged client.
